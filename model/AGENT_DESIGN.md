# DemandIQ Assistant — Design

The assistant is not a chatbot bolted onto a dashboard. It is a thin
conversational layer over the same services the UI calls, with one hard rule:
**it may only state things it can source from this workspace.**

## Identity and scope

The assistant inherits the caller's session. There is no separate login, and
no way to widen its reach by asking.

- Every tool call carries the user's `workspace_id`, `role`, and location
  scope. A viewer cannot have the assistant read an admin surface for them.
- Role shapes capability, not just visibility: operators get demand, forecasts
  and prep questions; administrators additionally get model, drift, pipeline
  and approval questions.
- Assistant turns are written to the audit log with the tools invoked, so a
  privileged read through conversation is as traceable as one through the UI.

## Tool surface

The model does not see the database. It sees a fixed set of typed tools, each
mapping to an existing endpoint from `backend/API_ENDPOINTS.md`:

| Tool | Backs onto | Returns |
| --- | --- | --- |
| `get_forecast(location, date)` | `/forecasts` | point, interval, model version, fallback flag |
| `explain_forecast(forecast_id)` | `/forecasts/{id}/explain` | SHAP attributions |
| `compare_policies(period, location?)` | `/policies/simulate` | SR, PS, UD per policy |
| `get_demand_history(location, range)` | `/demand` | daily series |
| `get_model_health()` | `/models`, `/models/{id}/calibration` | MAE, RMSLE, coverage, width |
| `get_pipeline_health()` | `/pipeline/runs`, `/quality/issues` | failures, gaps, drift signals |
| `get_locations()` | `/locations` | forecastability and blockers |

Tools are read-only. The assistant never promotes a model, changes a policy or
commits data — it hands off to the screen where a human does that, which is
why every answer can carry an action button.

## Answer contract

Every response the UI renders has four parts, and the middle two are not
optional:

1. **Headline** — one sentence stating the finding.
2. **Body** — the reasoning, in the operator's terms, with numbers.
3. **Figures** — the specific values, so nothing important lives only in prose.
4. **Sources** — which forecast id, model version, date range or job run was
   read. The panel shows this behind a "Based on N sources" disclosure.If no tool returns data that supports an answer, the assistant says what it
  does not have rather than interpolating. That refusal path is the fallback
  answer, not an error state: it is returned as a normal answer carrying
  `refused: true`, never as an HTTP error the caller has to interpret. A caller
  should not have to distinguish "the assistant declined" from "the assistant
  broke".

## Language rules

These are enforced in the system prompt and checked in tests:

- Never state kilograms of food waste. The platform simulates **surplus
  exposure in visitor-equivalents**; it weighs nothing. Asking for a weight is
  answered with that refusal — naming what the platform does report instead —
  rather than an error.
- Never present a SHAP attribution as a cause. "Contributed +18 covers", not
  "caused 18 more customers".
- Never give a point forecast without its range.
- Never recommend a preparation quantity without naming what it costs on the
  other side of the trade-off.
- Flag `fallback: true` forecasts as historical averages, not model output.

## Proactive insights

When the panel opens with no conversation, it shows up to three cards
generated by a scheduled pass, not by the model improvising:

| Kind | Trigger |
| --- | --- |
| Risk | A connector failing, a data gap, or coverage breaching tolerance |
| Opportunity | A weekday or location carrying a disproportionate share of surplus |
| Signal | Drift, a coverage shift, or a candidate model beating production |

Each card names its destination screen, so noticing and acting are one click
apart.

## Context awareness

The suggested prompts change with the active route — on the forecast screen it
offers "why did this move", on the pipeline screen "which jobs are failing".
The route id is passed as context so the assistant can resolve "this location"
or "this forecast" to what the user is currently looking at.

## Latency and streaming

- Tool calls run in parallel where independent.
- Target: first token under 800 ms, complete answer under 3 s.
- The UI shows a "reading your data" state rather than a generic spinner,
  because the honest description of the wait is that it is fetching, not
  thinking.

## What it deliberately cannot do

Menu costing, supplier pricing, staffing optimisation and profit estimates are
outside the data DemandIQ holds. The assistant states this boundary plainly
instead of producing a plausible number, because a confident wrong figure is
worse than an admitted gap in a tool people use to spend money.
